# CUMCM Math Modeling Codex Skill

面向全国大学生数学建模竞赛（CUMCM）的 Codex skill。它不是完整 Web/后端 Agent 系统，也不承诺自动生成获奖论文；它的定位是帮新手把数学建模过程理顺：先读题和检查附件，再确定建模路线，随后逐问求解、核对结果、整理图表和论文。

## 项目见解

数学建模竞赛里，AI 最容易出错的地方不是“不会写模型名”，而是：

- 没有读全题意和附件，只解决了一个相邻问题。
- Excel 多 sheet 没检查，数据覆盖不完整。
- 摘要、正文、表格、图和代码输出的数字不一致。
- 直接写“最优”“精度较高”，但没有可行性、误差或敏感性验证。
- 技术路线图好看但不可编辑，文字和箭头逻辑不可控。

这个 skill 的设计重点就是压住这些风险。使用时不需要了解内部工具和文件细节，只要用自然语言告诉 Codex 你要做什么，Codex 会在后台整理文件、检查数据、登记结果和做一致性检查。

## Codex 安装

在 Codex 中直接请求安装这个 GitHub 仓库：

```text
请安装这个 skill：https://github.com/usst-yk/cumcm-math-modeling-codex-skill
```

安装后重启 Codex。

使用时可以显式调用：

```text
[$cumcm-math-modeling] 请分析这道 CUMCM 题，先做题意拆解和建模路线设计。
```

## 使用指南

使用时尽量直接说目标，不需要说脚本名、文件名或技术细节。这个 skill 会按“读题 -> 查数据 -> 选路线 -> 求解 -> 验证 -> 写论文 -> 终审”的顺序推进；如果你只想做其中一部分，也可以直接指定。

### 1. 新建项目

适合刚开始做题，或者文件已经散乱时。它会帮你整理一个标准工作区，用来放题目、附件、代码、结果、图表、论文和检查记录。你只需要这样说：

```text
[$cumcm-math-modeling] 请为这道题新建一个项目，项目名为 2026A，后续所有材料都放在这个项目里。
```

### 2. 读题拆解

适合比赛刚开始。你可以把题目原文、截图文字或附件说明发给 Codex，让它先做题意拆解：

```text
[$cumcm-math-modeling] 我刚拿到这道题，还不知道怎么下手。请先帮我读题，拆解每一问要做什么、需要什么数据、最后应该交付什么结果。
```

你应该期待的输出是：每一问的任务目标、输入数据、约束条件、输出形式、可能的模型类型和风险点。

### 3. 完整推进全题

适合你希望 Codex 从头到尾推进整道赛题。它会按子问题逐问做，不会先空写整篇论文：

```text
[$cumcm-math-modeling] 请完整推进这道数学建模题。先拆题和检查附件，再设计三条建模路线，选定主路线后逐问求解、生成图表、登记关键结果，最后写出论文主体和提交前检查清单。
```

### 4. 只设计路线

适合比赛前期定方向，或者你们队还没有统一思路时：

```text
[$cumcm-math-modeling] 请给这道题设计整体建模路线。要求给出 3 种可选方案，说明每种方案的优缺点、实现难度、需要的数据、验证方式和论文表现力，最后推荐一条最稳妥的路线。
```

### 5. 只做某一问

适合老师只让你做其中一问、队友分工只负责一问，或者你想先把第 1 问做扎实。这个模式会只围绕指定问题展开，不把整道题铺开：

```text
[$cumcm-math-modeling] 只做第 1 问。请独立完成这一问：先分析题意和评分点，再给出 3 种建模路线，选择主模型，写出变量、假设、公式、求解步骤、验证方法，并给出可直接放进论文的中文段落。
```

没有真实数据时，它只会给模型和论文框架；有数据时，才应该生成最终数值、图表和结果段落。

### 6. 只写某一问论文

适合你已经有模型、代码或结果，只想把其中一问整理成论文内容：

```text
[$cumcm-math-modeling] 请只写第 2 问的论文部分。需要包括问题分析、模型假设、变量和符号、模型公式、算法步骤、结果解释、验证和敏感性分析、优缺点。没有数据支撑的数值不要写。
```

### 7. 检查附件数据

适合已经有 Excel、CSV 或其他附件，但不知道哪些表有用、有没有缺失或异常时：

```text
[$cumcm-math-modeling] 请检查我给的附件数据，看看有哪些文件和工作表、每列是什么意思、有没有缺失、异常、重复、时间范围问题，以及哪些数据可以用于每一问。
```

这个 skill 的原则是：有 Excel 就必须检查全部工作表，不能只看第一个 sheet。

### 8. 选择模型

适合你已经大概看懂题意，但不知道该用预测、优化、评价、仿真、聚类还是图论模型时：

```text
[$cumcm-math-modeling] 这道题我看懂了，但不知道该选什么模型。请按题型判断它更像预测、优化、评价、仿真、空间分析还是组合问题，并给出适合新手实现但不低级的模型路线。
```

### 9. 写代码求解

适合模型方向已经定了，准备开始计算时：

```text
[$cumcm-math-modeling] 请根据当前模型思路帮我写第 1 问的求解代码。要求能生成结果表和图，并说明每个关键结果来自哪里。不要把没有保存来源的数字写进论文。
```

### 10. 验证和敏感性分析

适合已经算出结果，但不知道怎么证明可靠时：

```text
[$cumcm-math-modeling] 我已经有了结果。请帮我设计验证和敏感性分析，说明应该和什么基线比较、看哪些误差或约束、哪些参数需要扰动，以及论文里应该怎么写。
```

### 11. 从结果写论文

适合已有代码、表格和图后写论文。这一步要求先看实际结果，再写文字：

```text
[$cumcm-math-modeling] 请根据当前已经算出的结果、表格和图片，把第 1 问写成论文段落。要求包含模型建立、求解过程、结果分析、验证说明和小结，论文里的数字必须能找到来源。
```

### 12. 收尾检查

适合论文主体接近完成后。可以分别要求写摘要、生成路线图或做评委视角终审：

```text
[$cumcm-math-modeling] 请根据当前论文和结果，帮我写摘要和结论。摘要要按每一问说明用了什么模型、得到什么结果、怎么验证，不能写空话，所有关键数字必须和结果表一致。
```

```text
[$cumcm-math-modeling] 请根据当前建模方案生成技术路线图，要求结构清楚、文字不要太密、适合放进数学建模论文，并附论文图注。
```

```text
[$cumcm-math-modeling] 请从评委视角检查当前论文和材料，重点看有没有答偏题、漏数据、数字前后不一致、图表不支撑结论、验证不充分、假设没有用上的问题。
```

更多细分场景见 `examples/README.md`，例如完整赛题、单问建模、代码到论文、路线图和最终审稿。

### 最后两小时补救

适合时间不够，需要保底交付时：

```text
[$cumcm-math-modeling] 现在只剩最后两小时。请帮我按优先级列出最该补的内容：哪些问题会严重扣分，哪些可以先不做，怎样保证论文和结果不矛盾。
```

### 队伍分工

适合队伍里有 2-3 个人，需要把建模、代码和论文同步推进时：

```text
[$cumcm-math-modeling] 我们队有 3 个人，请根据这道题帮我们安排 72 小时分工：谁负责建模、谁负责代码、谁负责论文，每个阶段应该完成什么，哪些结果必须互相同步。
```

## 常用需求速查

| 你想做什么 | 可以直接这样说 |
| --- | --- |
| 从零开始 | `请为这道题新建项目，并先做题意拆解。` |
| 只做一问 | `只做第 1 问，给出模型、求解、验证和论文段落。` |
| 只写论文 | `根据已有结果，把第 2 问写成论文部分，数字必须有来源。` |
| 不会选模型 | `请判断题型，并给出三条可选建模路线。` |
| 检查数据 | `请检查附件数据，尤其是 Excel 全部工作表、缺失、异常和重复。` |
| 做技术路线图 | `请生成可编辑的技术路线图，并附论文图注。` |
| 检查一致性 | `请检查摘要、正文、图表、表格和结果记录是否一致。` |
| 提交前查错 | `请从评委视角做最终审稿，按严重程度列出问题。` |

## Demo 和自检

提示示例集中放在：

```text
examples/README.md
```

仓库内置了一个完整小 demo：

```text
examples/full_problem_demo/
```

它包含题目、原始数据、任务计划、求解代码、图表、结果注册表、验证报告和论文片段，用来展示这个 skill 期望的交付形态。

仓库也提供轻量自检脚本，供维护者检查 demo 和 eval 提示是否完整：

```text
python3 scripts/run_skill_evals.py
```

普通学生不需要运行这些检查；它们主要用于维护 skill 的稳定性。

## 文件架构

```text
cumcm-math-modeling/
├── SKILL.md                  # skill 的核心说明
├── agents/                   # 不同工作阶段的角色提示
├── assets/                   # 论文和附录模板
├── examples/                 # 使用示例和完整 demo
├── evals/                    # 简单测试题
├── references/               # 更详细的建模规则
├── scripts/                  # 后台辅助工具，一般由 Codex 调用
└── templates/                # 项目模板
```

现在的设计是：`SKILL.md` 只做总入口和总规则，细节放在 `references/` 里，需要时再读取。这样 Codex 不会每次都加载一大堆规则，新手也不需要理解内部文件。

几个关键参考文件：

- `references/task-routing.md`：判断当前需求该走哪种流程。
- `references/correctness-ladder.md`：检查结果是否可靠。
- `references/workflow.md`：完整比赛流程和 72 小时节奏。
- `references/problem-routing.md`：不同题型的建模路线。
- `references/method-library.md`：常见建模方法库。
- `references/result-tracking.md`：论文数字如何追踪来源。
- `references/scoring-checklist.md`：提交前评分检查。

Codex 会根据任务自动使用后台工具，例如整理项目、检查数据、记录关键结果、检查论文数字和图表是否一致。新手不需要手动运行这些工具。

## 设计原则

- 先审题和审计数据，再建模。
- 先基线和可解释结构，再复杂算法。
- 按子问题逐问推进，不先写整篇最终论文。
- 先保存代码产物，再写论文结论。
- 每个关键数值必须进入结果注册表。
- 技术路线图优先可编辑源文件。
- 验证失败或输入不足时，记录阻塞项，不硬写最终结论。

## 边界

- 不保证获奖。
- 不替代人工确认关键假设。
- 不编造缺失数据、参考文献、指标、距离、排名或最优值。
- 不自动提交竞赛材料。
- 不把 Codex skill 变成完整 Web 应用或后端 Agent 服务。
